# Angular Enterprise Architecture — LLM-Ready Instructions (BOOK-Only)

> **Scope**: This document instructs an LLM how to structure an Angular application **strictly according to the BOOK**. It defines **what goes where, why, when, how**, and ends with an **EXTRA BIG exhaustive folder graph**.
> **Truth hierarchy**: BOOK only. If the BOOK is silent on a detail, the text says **“Not found — needs evidence.”**
> **Top-level types (do not rename)**: `core/`, `layout/`, `ui/`, `feature/`, `pattern/` (p. 66–67).

## Section 1 — Summary of Architecture (BOOK-Only)

### 1) The Big Picture & Types
- The architecture is composed of types with a clear **eager/lazy** boundary; **core**, **layout**, **ui**, **pattern**, and **feature** are all present (p. 66).
- Types map to folders (e.g., `core/`, `feature/`) to make navigation intuitive (p. 67).

### 2) Core (eager, headless, domain-grouped)
- Lives in `core/`. **Eager**, available from start, part of the initial bundle (p. 68).
- Holds **injector-based (headless)** building blocks: services, interceptors, guards, functions (p. 68).
- **Application configuration** via a central provider function (e.g., `provideCore`) for routing, HTTP, animations, state, and other providers (p. 70–71).
- **Domain-first** sub-structure is prescribed (e.g., `core/auth/`, `core/user/`, `core/product/`), **not** type buckets like `core/services/` or `core/reducers/` (p. 71).
- Limited exceptions for technical buckets (e.g., `core/interceptor/`, `core/utils/`) are acceptable (p. 71).
- **Extraction target**: when logic is reused by more than one **first-level** lazy feature, extract it into `core/` (headless) or `ui/` (presentational) — see p. 96.

**Placement rules (Core)**
- **Services**: `core/<domain>/...` when shared or needed from start (p. 68, p. 70–71).
- **Stores/State (shared across first-level features)**: if a store/state slice is required by **more than one first-level feature**, **extract it “one level up” into `core/<domain>/`** (p. 96, p. 100–102).
- **Interceptors**: global HTTP interceptors belong in `core/interceptor/` (p. 70–71).
- **Guards**: cross-app guards can live in `core/<domain>/` because core contains injector-based building blocks (p. 68).
- **Utils & Functions**: shared helpers live in `core/utils/` or under the relevant domain (p. 71).
- **Tokens/Configuration**: app-level providers and configuration are registered via `provideX` APIs in `provideCore` (p. 70–71).
- **Models/Interfaces**: domain contracts commonly live under `core/<domain>/` to avoid duplication across features (p. 70–71).
- **Mappers/Normalizers**: If domain mapping logic is reused across multiple features, place it under `core/<domain>/` as headless utilities (derived from domain grouping and headless placement, p. 70–71). **Term “normalizer”** — **Not found — needs evidence**.

### 3) Layout (global chrome)
- Lives in `layout/`. **Eager**. Contains only template-context building blocks (standalones) and acts as the **frame** around lazy features (p. 75).
- May consume **core** services/state and **ui** standalones (e.g., auth state for menus, avatar UI) (p. 75).
- Layout is separated from feature internals (p. 75).

### 4) UI (standalone presentational library)
- Lives in `ui/`. Contains **only standalones**: components, directives, pipes (template-context only) (p. 79–80).
- **Generic reusable** UI that communicates via inputs/outputs and **is not bound to state via services** (cannot import from `core/`) (p. 79).
- Usable from eager and lazy parts; bundler optimizes usage (p. 79–80).
- UI types can define **their own minimal interfaces** tailored to their view needs; mappings can happen in the consumer (p. 86).

### 5) Feature (lazy, isolated, co-located)
- Lives in `feature/<feature-name>/`. **Always lazy-loaded** via a route config; maintain **complete isolation** (features do not import other features) (p. 50–52).
- The **smallest app** is still one lazy feature, to keep a uniform model and extendability (p. 89, p. 106).
- A feature acts as a **black box** and may contain any implementation needed for that capability, co-located (p. 89).
- Heavy sub-capabilities can be nested as **lazy sub-features** when needed (p. 77–78, p. 89).

**Placement rules (Feature)**
- **Components/Directives/Pipes**: co-locate inside the feature; if used by multiple views within the same feature, keep them at the feature root (p. 89, p. 94–96).
- **Services & Stores (feature-only)**: co-locate when they serve only that feature; **extract to `core/<domain>/` when shared across first-level features** (p. 96, p. 100–102).
- **Shared between nested sub-features (same parent feature)**: **extract to the parent feature folder** (not `core/`), keeping isolation at feature level (p. 96).
- **Guards**: feature-only guards may live in the feature and be scoped to its routes (derived from feature as black box, p. 89).
- **Validators**: **Not found — needs evidence** as a named concept; by principle, reusable pure functions belong to `core/utils/`, while feature-only checks can be co-located (p. 68, p. 71, p. 94).
- **Models/Interfaces**: view-specific types may live in the feature; domain contracts shared across features belong in `core/<domain>/` (p. 86; p. 70–71).
- **Mappers**: when mapping logic is view-only, it can be local to the feature; when shared or domain-centric, move to `core/<domain>/` (derived from domain-first grouping, p. 70–71).

### 6) Pattern (reusable drop-in mini-features)
- A **pattern** is a reusable bundle of **standalones + injectables** used across multiple features (p. 94–96, p. 110).
- Patterns differ from UI (patterns may bind to data sources) and from Core (patterns include UI) (p. 100–101).
- Place shared pattern code in `pattern/<pattern-name>/`; consume via composition (p. 94–96, p. 110).

### 7) Sharing rules — “Extract one level up” (first-level vs sub-feature)
- **UI standalones**:
  - Reused by more than one **first-level** feature → **extract to `ui/`** (p. 96).
  - Reused by more than one **lazy sub-feature of the same parent** → **extract to the parent feature folder** (p. 96).
- **Core headless logic (services/stores/utils)**:
  - Reused by more than one **first-level** feature → **extract to `core/<domain>/`** (p. 96).
  - Reused by more than one **lazy sub-feature of the same parent** → **extract to the parent feature folder** (p. 96).
- **There is no “used more than three times” rule in the BOOK** — **Not found — needs evidence**.
- **Patterns**: use when reuse is a cohesive UI + headless bundle beyond a single presentational unit (p. 94–96, p. 110–111).

### 8) Dependency flow (one-way, isolation-friendly)
- The “one level up” extraction **removes dependency arrows between sibling lazy features**, enforcing isolation (p. 50–52).
- Respect the eager/lazy boundary and avoid crossing types in ways the BOOK forbids (p. 66, p. 75, p. 79).
